# Porno Blog

Простенький блог на PHP 8.4. Под капотом: Docker, Smarty, SCSS и Doctrine (ORM + Миграции).

---

## 🚀 Быстрый старт

**1. Настройка переменных окружения:**
Скопируйте конфигурационный файл-дистрибутив `.env.dist` в `.env`:
```bash
cp .env.dist .env
```
⚠️ **Важно:** Откройте созданный файл `.env` и убедитесь, что хосты баз данных настроены на имена сервисов Docker, а не локальные IP:
* `DB_HOST=db` (вместо `172.20.0.1`)
* `REDIS_HOST=redis` (вместо `172.20.0.1`)

Без файла `.env` сборка Docker-контейнеров упадет с ошибкой интерполяции.

**2. Поднимаем контейнеры (PHP, Nginx, MySQL, Redis):**
```bash
docker compose up --build -d
```

**3. Накатываем зависимости:**
```bash
docker exec -it blog-php-1 composer install
```

## 🗄️ База данных и фикстуры

Команды можно запускать прямо с хоста — они сами прокинутся в контейнер.

* **Сгенерировать миграцию (diff):**
  ```bash
  vendor/bin/doctrine-migrations diff
  ```
* **Применить миграции:**
  ```bash
  vendor/bin/doctrine-migrations migrate
  ```
* **Залить тестовые данные (фикстуры):**
  ```bash
  composer db:fixtures
  ```

## 🧪 Тесты

Пишем на **PHPUnit 9**, базу не трогаем — всё на моках.

**Как гонять тесты:**
1. Прыгаем в контейнер: `docker exec -it blog-php-1 bash`
2. Запускаем всё разом: `composer test`
3. Запустить один конкретный тест:
   ```bash
   ./vendor/bin/phpunit tests/Unit/UseCase/HomePage/HomePageIndexHandlerTest.php
   ```

> 🛠️ **Лайфхак:** Если при запуске тестов ругнётся Git (`fatal: detected dubious ownership`), просто выполни внутри контейнера:  
> `git config --global --add safe.directory /var/www`

## ⚡ Кэширование (Redis)

Для ускорения главной страницы используется система кэширования с умной инвалидацией по тегам. Тяжелые SQL-запросы к БД выполняются один раз, после чего готовые структуры DTO сохраняются в оперативную память Redis.

Переключение механизмов кэширования управляется из файла `.env` (переменная `CACHE_DRIVER`).

**Команды для ручной очистки кэша с хоста:**

* **Полностью очистить всю память Redis (Сбросить весь кэш):**
  ```bash
  docker exec -it blog-redis-1 redis-cli flushall
  ```
* **Посмотреть список текущих ключей и тегов в памяти:**
  ```bash
  docker exec -it blog-redis-1 redis-cli keys "*"
  ```

> 🛠️ **Лайфхак:** В коде используется паттерн **«Декоратор»**. Бизнес-логика в `UseCase` ничего не знает о существовании Redis, что сохраняет код чистым. Если в админке обновляется пост или категория, кэш сбрасывается автоматически с помощью инвалидации тегов (`posts_list`, `categories_list`).

Проект реализован как **MVP за 3 рабочих дня**. Стек полностью рабочий, код приведен в порядок, базовые уязвимости устранены. Готов к конструктивной критике, детальному разбору кодовой базы и обсуждению путей масштабирования архитектуры.

**Срок:** 3 рабочих дня при поддержке ИИ (архитектура и контроль – автор, ИИ – отладка и рутинные задачи).

## Архитектура и Инфраструктура

*   **Слоистый подход (Clean / Use-Case Driven):** Разделение на UseCase (бизнес-логика), Controller (HTTP) и Repository (база данных). Инфраструктурные модули полностью изолированы.

*   **Строгое соблюдение SOLID:**

  *   **SRP (Принцип единственной ответственности):** Каждый класс решает одну задачу. Логика очищена от побочного шума (кэширование, валидация).

  *   **DIP (Принцип инверсии зависимостей):** UseCase'ы и контроллеры зависят от интерфейсов репозиториев (`CategoryRepositoryInterface`). Детали Doctrine скрыты, что позволяет легко менять БД или мокать репозитории в тестах.

*   **Без фреймворков:** По ТЗ Symfony/Laravel запрещены, всё написано на Native PHP.

*   **Doctrine ORM:** Использована только для генерации миграций (`diff`) и проектирования схем.

*   **Кастомный IoC (Container):** Легковесный DI-контейнер на замыканиях в `index.php` для сборки зависимостей.

## Паттерны и Оптимизация

1.  **Фабричный метод + Стратегия (Формат ответа):** Формат ответа (JSON/Smarty) определяется в атрибуте роута контроллера `#[Get('/...', format: 'json')]`. Фабрика `ResponseStrategyFactory` на лету подменяет стратегию вывода.

2.  **Инверсия зависимостей + Стратегия (Трекинг посещений):** Сервис `PageViewTracker` принимает интерфейс `VisitStorageInterface`. Хранилище (сессии, файлы, Redis) подменяется в контейнере без правки кода трекера.

3.  **Декларативный маппинг (Attributes):** Входные параметры автоматически маппятся в DTO через атрибут `#[MapQueryString]`, разгружая контроллеры от ручной валидации.

4.  **Обратный роутинг (UrlGenerator):** Генератор URL сопоставляет ссылки по экшенам (`Controller@method`), полностью исключая хардкод путей в шаблонах.

5.  **ELT-фикстуры:** Написаны на чистом SQL (`CROSS JOIN + ELT(RAND())`). Заливают 500 000 записей за пару минут прямо в БД, минуя ORM.

6.  **Декоратор + Наблюдатель (Кэш Redis):** UseCase полностью изолирован от кэша. Инвалидация тегов автоматизирована через связку `EventDispatcher` и `InvalidateCacheListener` во Front Controller.

7.  **Шаблонный метод + Late Row Lookup (Пагинация):** Абстрактное ядро `AbstractIdBasedPaginatedHandler`. Сначала забирает плоский список ID по индексу, затем точечно делает JOIN строк. Скорость на дальних страницах – стабильный `O(1)`.

8.  **Пайплайн + Middleware (Роутер):** Роутинг на цепочке middleware. Сквозная логика (безопасность, CORS) полностью изолирована от контроллеров.

9.  **Валидация (Constraints):** Входные DTO проверяются через декларативные ограничения, разгружая код от ручных проверок типов.

10. **Решение проблемы N+1:** Ленивая загрузка связей заменена оптимизированными кастомными SQL-запросами.

11. **Безопасность (XSS):** Внедрена базовая защита от XSS при выводе. Полноценный пентест не проводился, за абсолютную надежность не ручаюсь.

12. **Осознанная денормализация под Highload (Идеальные составные индексы):** В рамках оптимизации Many-to-Many связей проведена принудительная денормализация таблицы `post_category` — поля `createdAt` и `views` вынесены напрямую в таблицу связей. На их основе созданы идеальные составные покрывающие индексы `idx_pc_category_created (category_id, createdAt)` и `idx_pc_category_views (category_id, views)`. Это позволило полностью объединить фильтрацию и сортировку на уровне B-Tree индексных страниц СУБД, ликвидировать файлы на диске (`Filesort`), убрать тяжелые `JOIN` при пагинации и снизить время связанных выборок в `PostRepository` до рекордных 0.36 мс на миллионных объемах.

13. **Сквозной профайлинг (Global Page Profiler):** Реализована кастомная система профилирования времени генерации страниц, которая активируется через конфигурационный флаг `APP_DEBUG`. Профайлер автоматически трекает статус кэша (HIT/MISS), считает суммарный тайминг рендеринга и перехватывает медленные SQL-запросы к СУБД, превышающие установленный лимит (более 50 мс), для их локализации и последующего аудита планов выполнения.


## ⚠️ Осознанные компромиссы и недостатки текущей реализации

1. **Ручная сборка DI в `index.php`:** Без автовайринга все фабрики настраиваются вручную. При росте проекта Front Controller раздуется (потребуются Service Providers).

2. **Лимит строки в ELT-фикстурах:** Запрос передает список ID категорий строкой из PHP. При огромном количестве категорий можно упереться в MySQL лимит `max_allowed_packet`.

3. **Отсутствие ЧПУ для пагинации:** В рамках MVP параметры пагинации передаются через Query String. На будущее требуется доработка роутера и Request Resolver’а.

4. **Фокус на бэкенд-архитектуру:** Стили написаны на SCSS строго по ТЗ. На фронтенде ориентируюсь свободно, но ключевая экспертиза – бэкенд и высоконагруженные запросы.

5. **Race Condition в трекере:** Проверка и лог визита идут последовательно (`hasVisit` -> `logVisit`). В Highload-среде возможен проскок дублирующего запроса.

6. **Привязка к реляционной БД в пагинации:** Оптимизация `Late Row Lookup` завязана на индексы MySQL. Переход на NoSQL потребует переписать абстракцию.

7. **Не везде соблюдалась строгая типизация (`strict_types`).**

8. **Не добавлены статические анализаторы (phpstan).** На продакшн проектах всегда добавляю.
